# Safety Map and Report a Spot

## OpenStreetMap tiles

The app uses `flutter_map` with OpenStreetMap raster tiles from `https://tile.openstreetmap.org/{z}/{x}/{y}.png`. No Google Maps API key or billing account is required. The map displays OpenStreetMap attribution and sends a stable Kavach user agent. Tile loading errors are surfaced with a retry action. The public OpenStreetMap Foundation tile service is best-effort, has no SLA, and must only be used within its [tile usage policy](https://operations.osmfoundation.org/policies/tiles/); use a dedicated tile provider or self-hosted tiles if production traffic requires guaranteed capacity. Tile requests go directly to OSM and disclose the viewed tile area and ordinary network metadata to that provider. Opening the Safety Map or starting a journey requests foreground location to center the map; users can deny permission and continue browsing the map or use a selected destination. The location control retries the request. There is no background location tracking. Approximate device location is accepted and the platform reported horizontal accuracy is retained in the selected point.

After foreground location is granted, nearby police stations and hospitals are queried within 5 km from the public Overpass API and shown as **OpenStreetMap mapped places**, not as verified emergency facilities. The request uses a location rounded to three decimal places and results are cached in memory for the app session. The user sees a disclosure that this approximate location is sent to OpenStreetMap. Missing places, outdated tags, provider outages, and incomplete coverage are possible; marker details say so. The public Overpass instance is shared and best-effort; it recommends caching/rate limiting and warns that applications with larger usage should run their own instance or use a provider. Configure a sustainable provider before broad production rollout. See the [Overpass public instance guidance](https://wiki.openstreetmap.org/wiki/Overpass_API#Public_Overpass_API_instances).

## Firestore collections and moderation

- `safetyReports/{reportId}` stores location, category (`unsafe` or `poorLighting`), time of day, optional note, `moderationStatus`, and server timestamp `createdAt`. A client batch creates each report as `pending` and creates a matching private authorship receipt in `safetyReportAuthors/{reportId}`. The public report has no author identifier.
- `safetyReportAuthors/{reportId}` stores only `authorUid` and `createdAt`, is readable only by its author, and cannot be changed by a client. It supports author-only pending access without exposing identity to map readers.
- `verifiedHelpPoints/{pointId}` is a manually maintained source. Only records with `type: policeStation`, `active: true`, and `verified: true` are read. Client writes are denied. Add only independently verified station records; no demo location is bundled.

The Firebase project owner moderates reports in Firebase Console by changing `moderationStatus` from `pending` to `approved` or `rejected`. Client updates and deletes are denied. Approval is moderation only and does not mean an observation was factually verified. The map queries only approved reports and the repository drops reports older than the rolling 30-day cutoff before creating markers. Direct reads are also time limited by rules. Firestore rules cannot prove a rolling `request.time - 30 days` condition from a list query, so approved expired documents remain readable through a direct collection query until separately deleted. They are not displayed by the Kavach map. **Physical deletion is not configured** and requires a separately configured Firestore TTL policy or owner cleanup process.

The public report query filters on moderation status; no composite index is expected. A report appears as a success only after its Firestore batch commit succeeds. Offline or rejected writes remain failures and can be retried. Notes are limited to 240 characters; the UI asks users not to include personal details. Approved notes are part of public report data and should be moderated accordingly.

## Validation and limits

Automated client tests cover location permission outcomes, report note length, coordinate bounds, map filter selection, expiry display policy, and duplicate submission prevention. Run Firestore rules tests with `npm run test:firestore-rules`; they cover authorship privacy, pending and approved reads, expiry visibility, field validation, and unauthorized moderation writes. No location or report workflow runs in the background.
