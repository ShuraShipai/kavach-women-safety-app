# Kavach Development Phases

Phases are sequential. Do not begin a later phase until its dependencies are met and the current phase's criteria pass. Future scope remains subject to product, safety, privacy, and platform review.

| Phase | Goal | Expected deliverables | Dependencies | Completion criteria |
|---|---|---|---|---|
| 1. Project inspection | Establish what exists in the app repository and sibling design. | Inventory of files, assets, actual screens, constraints, discrepancies. | None. | Findings are recorded without treating static mockups as working features. |
| 2. Documentation | Agree on product, design, architecture, coding rules, and roadmap. | `PRD.md`, `DESIGN.md`, `ARCHITECTURE.md`, `RULES.md`, `PHASES.md`, `MEMORY.md`. | Phase 1. | Documents agree on current project state, use verified evidence, and state unknowns. |
| 3. Flutter foundation and splash | Create the runnable Flutter foundation and implement the designed splash screen. | Flutter scaffold, app entry point, centralized theme/tokens, GoRouter setup, supplied logo asset, and splash widget test. | Phase 2; Flutter SDK and package/platform choices available. | Dependencies resolve, formatting and analysis pass, splash layout/assets are covered by a widget test, and no later screen or feature is pulled into this milestone. |
| 4. Design system | Implement reusable tokens and components from the verified deck. | Central color/type/spacing/radius tokens, ThemeData, accessible buttons/inputs/cards as needed. | Phase 3. | Tokens trace to `DESIGN.md`; component states and accessibility are reviewed on target sizes. |
| 5. Onboarding | Build Welcome through first-contact setup screens and recovery states. | Onboarding screens, permission rationale, form validation, navigation. | Phase 4. | Main onboarding path and denial/validation/back-navigation states work without claiming unavailable services. |

SOS | Implement the user-triggered alert review, countdown, cancellation, sending, and status. | SOS screens, state machine, repository/delivery adapter, honest outcome display. | Phases 6–7; delivery method and safety review. | Cancel and send paths are tested; each status reflects evidence and failures remain recoverable. |
| 9. Location sharing | Add consent-based current location to supported alert/journey actions. | Permission flow, location adapter, unavailable/stale states, sharing controls. | Phase 8; platform and privacy review. | Permission denial, unavailable fix, and stale data are surfaced; no background guarantee is implied. |
| 10. Firebase integrations | Connect only approved remote capabilities using FlutterFire. | Project-provided config, selected Firebase services, repositories, Security Rules and emulator tests. | Relevant feature requirements; Firebase project owner supplies configuration. | No guessed credentials; rules are reviewed/tested and app behavior works against emulator/test project. |

| 12. Later features | Add justified post-MVP design areas in reviewed increments. | Candidates: Vault, Shield, Journey Guardian, Map, Help/Guided Help, Settings/Offline Kit/Privacy Centre, Safety Assurance, voice trigger, battery handoff, decoy. | Phase 11 plus a feature-specific feasibility, privacy, and product decision. | Each feature has a defined owner/data policy/platform assessment, tests, limitations, and updated docs before release. |

## Current execution boundary

### Firebase integration progress (2026-10-25)

Firebase project `kavach-ac412` is registered for Android and iOS using the current `com.example.kavach` identifiers. FlutterFire configuration is generated and Firebase Core initializes at startup. The owner reports Phone sign-in enabled; runtime phone verification remains unverified until exercised on target devices. The default Firestore database is provisioned in Mumbai (`asia-south1`) with deletion protection. Owner-only rules compiled and deployed; no user records have been written. Profile and trusted-contact repositories use those rules. PINs are stored using Android Keystore/iOS Keychain secure storage. The Home 112 action offers a user-confirmed phone-app handoff, but device behavior is unverified. Permission handling, SOS alert delivery, and location sharing remain incomplete.

The onboarding permission screen now requests while-in-use location, camera, microphone, and notification permissions through the platform permission APIs. It shows current outcomes, supports opening app settings after permanent denial, and allows onboarding to continue when optional permissions are declined. Phone and messaging handoffs do not request runtime permissions. The permission dependency and Android/iOS usage declarations are added; dependency resolution and target-device checks remain pending.

Phases 1 and 2 are complete. The Flutter foundation and designed screens 1–10 are represented. Phone sign-in, profile persistence, secure PIN saving, and trusted-contact management are wired. Phone verification and Firestore app reads/writes still need device-level validation. Permissions, SOS delivery, and location remain prototypes. Runtime widget tests and target-device visual acceptance remain open.

Continue remaining onboarding, permission, and SOS functionality only with reviewed contracts and honest service outcomes. Do not describe a prototype action as successful.

### Evidence Vault progress (2026-10-25)

The Vault route supports local cases and notes, encrypted photos saved from Shield, 60-second audio/video capture, review-before-save, AES-GCM encrypted media files, SHA-256 hashes, device timestamps, a saved-recordings list, evidence deletion, and multi-page PDF reports. Validate capture permissions, open/share handoff, encryption, and deletion on target devices before release. SOS automation, location capture, and retention controls remain unimplemented.

Screens 14–22 are represented in the app: Vault list, case timeline, export preview, Shield home, message input/progress/result, and image/video selection, consent, and result. Image/video analysis is wired to a Firebase callable backend source using Resemble, but is not live until Functions/Storage are deployed and the API key secret is configured. An image can be saved encrypted from the result page. Static checks and Android debug build pass; no target-device run is recorded for these flows.
